        芯片内置OTP资源

        OTP是一种特殊的非易失性存储器，允许编程一次，数据永久有效。利用OTP一次性编程的物理特性保存一些不可逆控制开关、硬件根密钥等。其中，密钥区域提供多个对称根密钥Slot，用于存储多个对称根密钥。密钥区域只能一次烧写，自动锁定，且不可回读。状态控制区域和用户自定义区域，可多次烧写，对应比特位只能由0编程为1，已经为1的比特不可更新；如果需要一次烧写后，其内容不可更改，则可在数据写入后，锁定该区域。版本控制区域可多次烧写，所有比特只能由0写为1，不可逆，也不可锁定。

        内置密钥管理模块

        对于已经烧写进OTP的每一个对称根密钥，密钥管理模块会根据相应的外部输入（密钥派生材料），进行多级派生，生成对应的工作密钥，并将工作密钥直接送到加解密引擎，实现对最终的数据进行加解密运算。整个密钥派生过程都在硬件逻辑内部完成，根密钥、密钥保护密钥、工作密钥都不会在内存中出现，也不能通过软件读取，提升了密钥的安全性。

        镜像结构统一

        安全启动和非安全启动镜像结构统一，适用于产线烧写场景。在没有镜像加密的情况下，可以直接烧写安全镜像到没有烧写 OTP 的裸设备并通过非安全启动流程启动。烧写安全 OTP 后通过安全流程启动。

        安全启动涉及较多的密钥和签名，需要附加在最终镜像中。为避免镜像制作和使用过程因多个版本而引入的各种问题，降低使用难度，本启动方案将安全启动、非安全启动的所使用的镜像统一为一种格式。在SoC不使能安全启动的情况下，非加密的安全启动镜像（带有对应的公钥和签名），仍可正常启动。

        安全模拟

        安全模拟功能仅适用于OEM安全启动调试阶段，防止误烧 OTP 造成芯片不可用。

        安全模拟包括两部分功能：一方面是对镜像验签模拟，另一方面是对镜像加解密模拟。

        安全验签模拟功能表示仅通过 Flash 镜像中的标识决定是否使能校验。不需要烧写校验使能 OTP，只需烧写校验所需的根公钥Hash。一旦发现 OTP 误烧，安全校验不通过，可以通过重烧非安镜像启动设备。

        安全加解密模拟功能表示仅通过 Flash 镜像中的标识决定是否使能加解密。不需要烧写解密使能 OTP，只需烧写校验所需的root key，便可以对镜像加解密进行模拟。

        注意：
        只有No TEE安全模拟的SoC可以通过重烧非安镜像启动设备。

        支持TEE OS安全内核

        安全启动方案支持从硬件->可信根->BOOTROM->SecureBootloader(GSL)->TEE OS以及REE侧各部分的可信校验，即TEE信任链和REE信任链分离。

        启动阶段Flash提频

        加速启动镜像读写，提高启动速度。启动阶段 Flash 接口时钟频率可选。

        安全boot镜像备份

        在安全启动场景下，支持烧写一个备份 Boot Image。当主 Boot Image 校验失败，引导程序会从启动介质搜寻可用的备份 Boot Image，并引导启动。

        多boot表格

        支持在镜像中配置多个boot表格，通过修改 GSL 代码中多表格函数钩子，实现一个镜像可适配多种板型。

        根公钥校验

        通过在板端计算根公钥的Hash值和OTP 中的值比较实现校验。Hash 算法可通过 OTP 选择为 SHA256 。

        外部公钥对镜像校验

        外部公钥对 Code 区的校验相对复杂。镜像布局和验签关系见图1。需要通过根公钥->Key Area->Code Info->Code这一验签链实现完整的镜像验签。

        外部公钥保存在 Key Area里。对 Key Area的验签需要通过根公钥或者已经被校验过的上一级外部公钥实现验签。Key Area 中包含了上一级公私钥对的签名。

        外部公钥被验签完成后，使用外部公钥对 Code Info验签。外部公钥的签名被保存在 Code Info 区。

        Code Info 中保存了 Code 的 Hash 值，通过比较镜像Code区的 Hash 值和保存在 Code Info 中的 Hash 值可以确保镜像没有被篡改。

        版本防回滚

        在验签过程中，会将签名后的镜像中 version 字段和 otp 中的值比较。防止使用有风险的老版本镜像实现恶意攻击。

        校验条件： version_ext & mask_version_ext 中高位的个数大于等于 otp_ver & mask_version_ext 中高位的个数。

        有些镜像中 key 区和 info 区中有各自的 version 字段，但是都是和同一个 otp 比较。可以通过 key 区的 version mask 把 otp 划分出 key 区校验位域与 info 区校验位域。

        例如：

        某一 otp 中的 version 占用 8 bit。高 4 bit 分给 key 区的 version，低 4 bit 分给 info 区的 version。

        则 key 区 version mask 应该配成 0b11110000。key 区的 version 按照 0b00010000，0b00110000，0b01110000，0b11110000 递增。

        info 区的 version mask 应该配成 0b00001111。info 区的 version 按照 0b00000001，0b00000011，0b00000111，0b00001111 递增。

        注意：
        1、tee code info的版本防回滚检查方式比较特殊，它的version_ext无需和掩码mask_version_ext进行与运算，而是直接给定自然数。如：tee code info区的version_ext给定0x10（自然数为16）
        2、tee key area和tee code info的版本防回滚检查共用了一个64bit的otp_ver，当tee key area的掩码mask_version_ext 决定用多少个bit后，剩下的bit均可供tee code info使用。
        3、tee key area的version_ext不能超出32bit。

        加解密

        用于镜像加解密的算法可选为AES。

        考虑到实际业务中存在多种加解密场景，出于安全性考虑不同加解密场景会使用不同的密钥。SoC 中提供了一种，只烧写一个 OTP 并生成不同的加解密密钥的方式。实际用于加解密的密钥一般称其为工作密钥，由芯片内部的 KM 模块生成。

        图 1 KM模块工作机制

        镜像制作工具在 PC 端模拟了工作密钥生成过程，并在 PC 端进行加密。镜像解密场景下加扰后的根密钥特指 Obfu_MRK1。

        密钥派生材料和加密后的密钥都是存储在镜像里的字段，是公开信息。影响工作密钥的值，但是不影响工作密钥的安全性。

        KM 模块生成工作密钥后会直接在硬件中送给 SPACC 模块，软件不可读。SPACC 收到工作密钥后应用 AES 解密算法对镜像解密。

        根密钥

        根密钥在安全启动里特指 Obfu_MDRK1，需要烧写到 SoC 中的 OTP 里，并且需要和配置文件中 oem_root_key 字段保持一致。 Obfu_MRK1 和 MRK1一 一对应但是并不相等。Obfu 前缀表示加扰的意思。目前各个OEM厂商所使用的加扰方法相同，加扰起不到保护作用。板端解密用到的 MRK1 烧写在 OTP 中，烧写方法请见《Hi35xxVxxx 安全子系统使用说明》"OTP" 章节。

        建议在安全服务器上使用 openssl rand -hex 16 命令生成。并保存在安全服务器上。

        和上面提到的公私钥不同，加解密用的是对称密钥。

        密钥派生材料

        密钥材料是镜像中涉及密钥派生字段的统称，这些字段和根密钥一起派生对镜像加解密的密钥（一般称其为工作密钥）。

        KM 模块

        加解密密钥管理模块，向 SPACC 模块配置加解密密钥。具体请见《Hi35xxVxxx 安全子系统使用说明》。

        SPACC 模块

        支持以下安全特性：

        • 对称加解密算法
        • HASH 算法和非对称加解密算法
        • 验签算法

        具体请见《Hi35xxVxxx 安全子系统使用说明》。

        内核及文件系统安全启动校验

        该方案是基于上述安全启动方案的特性，在U-Boot验签通过后，再通过在U-Boot上实现验签内核的功能。前一阶段系统引导下一阶段系统前，先对待启动系统进行验签，如果验签成功，再启动Linux系统，否则系统启动失败。验签机制可以保证系统镜像的完整性，如果镜像被篡改或损坏，系统将不会被启动。

        • 安全启动流程

        • U-Boot 支持安全启动配置

        安全镜像结构

        安全镜像由 Key Area、Code Info Area 和原始镜像三部分组成，如图1所示。

        图 1 安全镜像结构图

        1. Key Area 保存了 External Public Key和对 Key Area Body 区域的签名，该区域使用 U-Boot 代码中的 Root Public Key进行验签来保证其完整性。
        2. Code Info Area 里保存了原始镜像的hash值和对Code Info Area Body区域的签名，该区域使用Key Area中的 External Public Key 进行验签来保证其完整性。
        3. Code Area 为原始镜像，该区域通过计算其 hash 值，与 Code Info Area 中保存的 hash 值进行比较来保证其完整性。

        警告：
        reserved4 区域未经过校验，因此无法保证其数据完整性，在该区域中不应该保存任何有效信息。

        rsa验签镜像制作

        本节提供通过shell命令完成安全镜像制作，以 kernel.bin 镜像为例，最终得到安全镜像 kernel_sign.bin。

        建议用户新建一个目录，将编译的镜像ulmage重命名为kernel.bin，拷贝到新建目录下，执行以下命令，用于生成rsa验签镜像。

        1. 生成两个私钥文件

          openssl genrsa -out root_private_key.pem 3072;
openssl genrsa -out extern_private_key.pem 3072;

        2. 制作 Key Area 镜像

          dd if=/dev/zero of=image_key_area_1.bin count=252 bs=1
openssl rsa -in extern_private_key.pem -modulus -noout | sed 's/Modulus=//'| xxd -r -p > modulus.bin
echo "00010001"| xxd -r -p > exponent.bin
cat image_key_area_1.bin modulus.bin exponent.bin > image_key_area_body.bin
openssl dgst -sha256 -sigopt rsa_padding_mode:pss -sign root_private_key.pem -out image_key_area_signature.bin image_key_area_body.bin
cat image_key_area_body.bin image_key_area_signature.bin > image_key_area.bin

        3. 制作 Code Info Area 镜像

          dd if=/dev/zero of=code_info_area_1.bin count=36 bs=1
printf "%08x" $(wc -c < kernel.bin) | sed -r 's/(..)(..)(..)(..)/\4\3\2\1/g' | xxd -r -ps > code_area_len.bin
sha256sum kernel.bin | awk '{printf $1}' | xxd -r -ps > code_area_hash.bin
dd if=/dev/zero of=code_info_area_2.bin count=184 bs=1
cat code_info_area_1.bin code_area_len.bin code_area_hash.bin code_info_area_2.bin > code_info_area_body.bin
openssl dgst -sha256 -sigopt rsa_padding_mode:pss -sign extern_private_key.pem -out code_info_area_signature.bin code_info_area_body.bin
dd if=/dev/zero of=sig_code_info_ext.bin count=384 bs=1
cat code_info_area_body.bin code_info_area_signature.bin sig_code_info_ext.bin > code_info_area.bin

        4. 制作最终签名镜像

          cat image_key_area.bin code_info_area.bin kernel.bin > kernel_sign.bin

        U-Boot 支持安全启动配置

        1. 编译 U-Boot 时添加 Verify Boot 支持

          在编译 U-Boot 时执行 make ARCH=arm menuconfig 命令进入配置选择页面，依次进入 Product ---> verify boot enable，按 Y 选中保退出并保存。

          cd third_party/u-boot/u-boot-2022.07
cp configs/hi35xxvxxx_debug_defconfig .config
make ARCH=arm menuconfig  //使能product下的verify boot enable
cp .config configs/hi35xxvxxx_debug_defconfig   //拷贝.config文件为默认配置文件

        2. 在 U-Boot 代码中填入 Root Public Key 公钥

          修改 Hi35xxVxxx_SDK_Vx.x.x.x/open_source/u-boot/u-boot-2022.07/product/verify_boot/verify_boot.c 文件，非国密安全启动将 root_private_key.pem 中的公钥对（N，E）填入 g_root_pub_key 数组；国密安全启动将kernel_external_pubkey.bin公钥填入g_root_pub_key 数组。

          说明：
          - 可使用 openssl rsa -in root_private_key.pem -modulus -noout | sed 's/Modulus=//'| xxd -r -p > modulus.bin 从私钥中导出 N，E 的值固定为 4 Bytes 的 {0x00, 0x01, 0x00, 0x01}，打印N的命令为xxd -i modulus.bin
          - RSA算法支持二级校验，保证Key Area和Code Info Area区域的完整性，Key Area验签需要开启宏CONFIG_VERIFY_KEY_AREA_SUPPORT，开启目录：Hi3511CV100_SDK_Vx.x.x.x/open_source/u-boot/u-boot-2022.07/product/verify_boot/Makefile
          - 国密算法只支持一级校验，保证Code Info Area区域的完整性，执行xxd -i oem/tmp/kernel_external_pubkey.bin 打印出公钥

        3. 重新编译 U-Boot 即可。

        上述步骤编译的 U-Boot 镜像会增加一条 verify_boot 命令，需要修改 bootcmd 才能最终开启安全启动功能。

        bootcmd 修改参考如下（以 kernel 镜像为例，flash 介质为 spi nor，其位于 flash 1M 偏移，大小为 4M）：

        不开启安全启动时，bootcmd 命令为：sf probe 0; sf read 0x41000000 0x100000 0x400000; bootm 0x41000000;

        开启安全启动后，bootcmd 命令应该修改为：sf probe 0; sf read 0x41000000 0x100000 0x400000; verify_boot kernel 0x41000000; bootm 0x41000800;

        修改点主要是两个地方：

        1. 将镜像从 flash 读到 ddr 后，需要先使用 verify_boot 命令传入两个参数（镜像名和 ddr 地址），该命令会校验位于该 ddr 地址的镜像的合法性，若校验不通过则系统复位。
        2. bootm 启动地址需要增加 0x800 的偏移，因为支持安全启动后，镜像会增加 0x800 的镜像头信息。

        警告：
        调试时可以在 U-Boot 命令行中修改 bootcmd 命令，但在量产版本中不允许启动时进入 U-Boot 命令行，必须将 bootcmd命令在 U-Boot 编译时配置好。

        安全Boot 镜像备份功能

        Boot 镜像备份指的是在介质中存放两个Boot 镜像，其中从0地址开始的第一个Boot分区为主分区，第二个Boot分区为备份分区，当主Boot 镜像校验失败（包括key、gsl、uboot区域）后，便软复位从介质中搜寻备份分区起始地址标志，匹配成功后重新从备份分区启动。

        如需使用安全 Boot 镜像备份功能，请先烧写安全 Boot备份启动对应的OTP。OTP定义详见《Hi35xxVxxx 安全子系统使用说明》的OTP章节中“boot_backup_enable”字段。

        注意：
        - 仅支持备份1个 安全Boot Image，且备份Boot Image需放置在主Boot Image之后。
        - 当存储介质为Flash时，备份镜像最大SIZE:512KB；当存储介质为emmc时，备份镜像最大SIZE:2M。
        - 烧写的备份 Boot Image 起始地址要求64K对齐。
        - 当存储介质为spi nand时，第一个block不能擦除或者损坏。

        多Boot表格功能

        在镜像制作工具中配置多个boot表格（见 Boot 表格 Info 区配置项）。并修改 gsl/boot/board_type.c代码中多表格函数钩子get_board_param_index() 实现一个镜像适配多种板型。

        下面以demo板为例进行使用说明：

        1. boot_param_file0-7为镜像脚本工具中.json文件配置项，位于配置文件boards/dmeb/tools/pc/image_tool/oem/quick_build_config.json中，即SDK版本包默认编译的非安场景配置文件；另外同级目录下的quick_build_secure_boot_config.json为安全non-TEE场景使用，quick_build_tee_config.json为安全TEE场景使用，请按需选择。

        2. 指定单个表格文件路径方法

          例如配置"boot_param_file7": "./input/reg_info.bin"，需要将表格文件reg_info.bin放入镜像工具相对路径boards/dmeb/tools/pc/image_tool/input中，编译时会自动编译进入boot_image.bin中，也可以指定为表格文件的绝对路径，请按需配置。

        3. 指定多个表格文件路径方法

          例如同时配置3个表格："boot_param_file0": "./input/reg_info0.bin"，"boot_param_file3": "./input/reg_info3.bin"，"boot_param_file7": "./input/reg_info7.bin"，编译时reg_info0.bin、reg_info3.bin，reg_info7.bin 3个表格都会自动编译进入boot_image.bin中；也可以指定为表格文件的绝对路径，请按需设置。

        4. 总体示例

          如在镜像表格文件配置项中boot_param_file0和boot_param_file7给定了boot表格路径，当配置get_board_param_index()的返回值为0，则启动时会选择boot_param_file0对应的boot表格，当配置get_board_param_index()的返回值为7，则启动时会选择boot_param_file7对应的boot表格。

        注意：
        - boot表格个数最大不超过8个，boot表格bin文件大小最大不超过15KB。
        - 以上json文件修改只能修改规定预留区域，即双引号内预留的填充区，不能删除或增加行数，否则会存在编译表格镜像与拨码不匹配问题。

        维护模式

        维护模式适用于海思需要在OEM设备上调试安全设备的情况。该设备已经被OEM烧写了根公钥，避免每次重烧镜像都需要 OEM 重新签名。调试 key 和 DIE_ID（每个芯片有唯一的 DIE_ID） 绑定，保证调试 key无法在设备间共用。调试结束后 OEM 重烧 OTP 使海思调试 key 失效。此模式可以解决在调试场景下海思和 OEM 之间互信的问题。

        图 1 维护模式镜像制作

        如图1所示。海思会根据实际情况提供 GSL，U-Boot，TEE OS 的调试外部公钥。

        OEM 拿到调试外部公钥后使用镜像制作工具生成维护模式镜像。启用维护模式需要参考维护模式相关配置项 中的描述，打开对应选项。镜像中的 DIE ID，维护模式标记，KEY 区版本，海思调试公钥被一起验签，海思无法篡改。

        结束调试后，OEM 根据实际情况来烧写以下 OTP失效海思调试公钥：

        • tee_boot_ver：对应 GSL 外部公钥
        • ree_boot_ver：对应 U-Boot 外部公钥
        • tee_os_ver：对应 TEE OS 外部公钥

        失效原理请参考版本防回滚，OTP 烧写请参考《Hi35xxVxxx 安全子系统使用说明》。

        注意：开启第三方验签的设备无法使用维护模式。
