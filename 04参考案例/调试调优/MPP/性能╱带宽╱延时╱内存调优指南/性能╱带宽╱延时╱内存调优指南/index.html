    性能调优

    性能优化的通用方法一般有：硬件加速、优化perf热点函数、优化ftrace调度阻塞、优化大线程。

    性能优化的第一步应该是找出需要优化的重点对象：top观测到的大线程、perf火焰图指示的热点函数、ftrace追踪图指示的受阻塞函数、频繁的无效调度、频繁的动态申请资源、碎片化操作过多、多级节点串行处理等。第二步再打开重点对象的内部流程，进行有针对性的优化。

    性能优化方法有：硬件加速、绑核分摊负载、线程优先级调整、批处理、并行处理、大量数据CPU读写采用cache、大数据量memcpy DMA化、减少无效调度、动态申请资源改为静态、减少无效打印、关闭冗余功能等。

    性能优化分析工具：perf、ftrace、top、proc、bspddrs、仿真器，业务流程需人工分析。

    本章节提供了一些SDK系统性能相关的调度策略，客户需要根据业务实际情况进行调节测试。

    • 操作系统调度

    • 媒体驱动调度

    操作系统调度

    操作系统的默认调度策略具有普遍适用性，不建议轻易尝试修改系统的默认调度策略，有性能问题的特定场景可尝试修改调整，调整后的配置只适用于验证过的特定场景，不适用于直接移植到其它未验证过的场景。

    中断绑核

    系统中的中断默认都没有绑定CPU亲和性，因此中断默认都会报到CPU0上，如果CPU0的中断数量太多影响到了业务性能、帧率等情况，可以尝试调整部分中断号的CPU亲和性，把一部分中断号绑定到其它CPU上，减轻CPU0的中断压力。

    查看中断信息：cat /proc/interrupts

    查看中断亲和性：cat /proc/irq/中断号/smp_affinity

    修改中断亲和性：echo 中断位掩码 > /proc/irq/中断号/smp_affinity

    针对中断绑定CPU的操作有如下建议：

    • 绑定CPU的操作要在业务运行之前进行，不要在业务运行过程中动态切换绑定；
    • 除VICAP之外，一般建议同一个模块的多个核要绑在同一个CPU上；
    • 把中断比较多的模块识别出来绑定到其它CPU上，比如网络的中断若比较多，可以把它跟媒体业务分开。

    进程绑核

    当某个进程需要较高的运行效率时，可以考虑将其绑定到单独的核上运行，以减小由于在不同的核上调度造成的开销。把某个进程/线程绑定到特定的cpu核上后，该进程就会一直在此核上运行，不会再被操作系统调度到其他核上。但绑定的这个核上还是可能会被调度运行其他应用程序的。

    进程绑核相关接口：

    int sched_setaffinity(pid_t pid, size_t cpusetsize, cpu_set_t *mask);

    int sched_getaffinity(pid_t pid, size_t cpusetsize, cpu_set_t *mask);

    线程调度和绑核

    当系统中某个业务线程的实时性要求较高，出现调度不及时影响帧率等性能问题时，可以尝试调整单个线程的优先级、线程调度策略，或者预留一个CPU给某个线程独享，其它非及时性线程与这个实时性线程分开绑定到不同CPU。

    • 线程调度策略：线程有三种调度策略，如下

      • SCHED_OTHER：分时调度策略。不支持线程优先级
      • SCHED_FIFO：实时调度策略，先到先服务。一旦占用CPU则一直运行，直到有更高优先级任务到达或者自己放弃。支持线程优先级。
      • SCHED_RR：实时调度策略，时间片轮转。支持线程优先级。

      线程调度策略相关接口：

      int pthread_attr_setschedpolicy(pthread_attr_t *attr, int policy);

      int pthread_attr_getschedpolicy(const pthread_attr_t *attr, int *policy);

    • 线程调度优先级：线程调度优先级支持从1到99，数值越大优先级越高，越先被调度。

      线程优先级相关接口：

      int pthread_attr_setschedparam(pthread_attr_t *attr, const struct sched_param *param);

      int pthread_attr_getschedparam(pthread_attr_t *attr, struct sched_param *param);

      int sched_get_priority_max(int policy);

      int sched_get_priority_min(int policy);

    • 线程绑核：操作系统的默认线程调度机制是没有问题的，线程能被所有核调度到。但是，当某个线程需要较高的运行效率时，就有必要考虑将其绑定到单独的核上运行，以减小由于在不同的核上调度造成的开销。把某个线程绑定到特定的cpu核上后，该线程就会一直在此核上运行，不会再被操作系统调度到其他核上。但绑定的这个核上还是可能会被调度运行其他线程的。

      线程绑核相关接口：

      int pthread_setaffinity_np(pthread_t thread, size_t cpusetsize, const cpu_set_t *cpuset);

      int pthread_getaffinity_np(pthread_t thread, size_t cpusetsize, cpu_set_t *cpuset);

    • 线程休眠时间对CPU也有影响，线程休眠时间太短、无效调度次数过多会导致CPU占用升高，线程数量越多影响越大。因此需要根据业务需要设置合理的休眠时间，建议优先使用wait和wakeup机制，条件满足时才唤醒线程运行。

      说明：
      - 调试时可以使用chrt命令临时查看或修改线程调度策略和优先级：

      例：
查看线程调度策略和优先级：chrt -p <pid>
修改线程调度策略和优先级：chrt -r -p <priority> <pid>

      - 调试时可以使用taskset命令临时查看或修改线程绑核：

      例：
查看线程绑核命令：taskset -p <pid>
修改线程绑核命令：taskset -p <cpu_set> <pid>
<cpu_set>：设置值为1指绑到CPU0上，2指绑到CPU1上，3指同时绑到CPU0和CPU1上随机调度。

      • 优先优化切换次数多的线程
      • 合并任务，减少线程（同一进程内存在多个对时间不敏感的任务，可以将其合并成一个任务，定期执行）
      • 频繁的轮询模式改成事件驱动，或者事件驱动与查询结合
      • 减少锁等待，A线程执行完唤醒B线程执行这类情况可合并线程取消锁

    HZ

    SDK版本配置的Linux内核HZ默认是100，对应一个jiffies为10ms。当系统需要更高精度的线程、定时器调度要求时，可以把HZ设大，但产生的影响是CPU占用会上升。

    方法是修改内核宏CONFIG_HZ的定义值。

    大数据量拷贝

    大数据量拷贝尽量避免使用CPU，尽量使用DMA代替。如果一定要使用CPU，cache方式比非cache方式拷贝效率高。但要注意，如果存在CPU和其它硬件IP都访问同一块buffer且CPU以cache方式访问，则CPU访问前后必须配合正确的刷cache操作，否则CPU和其它外设访问到的数据有可能是不一致的。

    NPU/IVE硬件加速

    智能处理中的一些纯软件计算可以使用NPU/IVE硬件加速替换CPU，比如：

    • 检测网后处理(Filter/Sort/NMS)可使用NPU的DetectionOutput层硬化加速。
    • IVE算子取代部分CPU算子，比如Resize/GMM2/Dilate/Erod/KCF等。

    模块替代

    • 有缩放能力的模块有VGS/IVE/NPU，媒体缩放建议使用VGS，智能缩放建议使用IVE和NPU。如果某个模块业务压力过大性能不足时，也可考虑使用其它业务压力小的模块代替。
    • 有DMA能力的模块有IVE/VGS/TDE，可根据业务压力均衡调度。大数据量拷贝尽量使用DMA代替CPU拷贝。

    调整USB中断间隔

    USB 协议通过中断间隔参数来控制设备向主机请求数据传输的频率。对于USB设备，合理调整中断间隔能够显著影响传输性能。

    • 较小的中断间隔：更频繁的数据请求，降低延迟，提升实时性，但增加CPU开销。
    • 较大的中断间隔：减少中断频率，降低CPU占用率，但会增加延迟，降低峰值吞吐量。

    在内核USB Device模式下，Hi3511CV100的USB控制器设置USB中断默认间隔为无间隔，此时传输速率最高，但相应增加批量数据传输时的CPU占用率10%~20%。

    若无需高速率传输且希望减少CPU占用，可采用以下两种方法之一设置中断间隔。

    1. 修改内核代码。进入到版本路径下third_party/linux/linux-5.10.y/drivers/usb/hiusbc/hiusbc_core.h文件，修改宏定义：

      #define HIUSBC_IMODI_NO_INTERVAL 0

      默认值为0，即无中断间隔。单位为250ns，例如值设置为4000，则中断间隔为1ms=4000 * 250ns。

      修改完成后重新编译内核。

    2. 开启内核debugfs。

    3. 进入内核menuconfig的如下路径，确认以下驱动配置选上。

      Kernel hacking --->
    Generic Kernel Debugging Instruments --->
        [*] Debug Filesystem

    4. 编译内核，编译方法参照：bsp/readme_cn.txt中“单独编译kernel image”步骤流程；

    5. 启动内核后，执行以下命令。

      修改中断间隔，如将中断间隔调整为1ms(4000 * 250ns = 1ms)，参考如下命令。(中断间隔默认为0)

      mount -t debugfs none /sys/kernel/debug
echo 4000 > /sys/kernel/debug/usb/10500000.usbc/imodi

      查看中断间隔，参考如下命令。

      cat /sys/kernel/debug/usb/10500000.usbc/imodi

    注意：
    - 以上步骤仅适用于Hi3511CV100内核USB Device模式。
    - 命令中的"10500000.usbc"对应USB Port0口，USB Port1口对应"10540000.usbc"，请根据实际需求调整命令。(以Hi3511CV100 demo板usb3.0_0为例，后缀_0表示Port 0口)
    - imodi写入单位为250ns，最大值为4000，即间隔最大为1ms，最小值为0，即无间隔。

    综述

    带宽调优主要是降低单位时间内DDR的载入载出数据量和访问DDR的命令次数。主要优化方向有：

    • 能用在线模式就不要使用离线模式，在线、离线与场景规格有关。在线模式数据不需要写出DDR，可节省带宽。
    • 能用压缩就不要使用非压缩。压缩之后数据量会减少，可节省带宽。
    • CPU能用cache方式访问DDR就不要使用非cache方式。相同的数据量读写，CPU使用cache方式访问DDR的命令次数比非cache方式少很多。注意，如果存在CPU和其它硬件IP都访问同一块buffer且CPU以cache方式访问，则CPU访问前后必须配合正确的刷cache操作，否则CPU和其它外设访问到的数据有可能是不一致的
    • 所有调优措施都使用之后，如果带宽依然达不到要求，可能就要从产品的系统业务层面做一些取舍，比如降低帧率、降低raw数据位宽、降低图像分辨率、裁剪一些非关键的业务等等。

    综述

    DDR小型化可以从多个方向入手：uboot、kernel、filesys、SDK、APP都可以在内存使用上做一定程度的优化。本文主要是对SDK和APP的小型化进行简单的说明，uboot、kernel、filesys的小型化请参考《Hi35xxx 系统小型化说明》。

    DDR小型化按收益大小，一般建议的分析先后顺序为：

    1. 优化媒体通路数据流：首先画出整个系统的媒体通路业务数据流，然后逐级分析每个模块前后级之间的连接方式是否内存最优，不是内存最优的重新调整数据流。
    2. 优化媒体VB个数和VB大小：主要查看VB proc信息的min_free确认VB个数是否设置过多和free_bytes确认VB大小是否设置过大。具体参考“VB”章节。
    3. 优化媒体模块内存相关配置：一般有压缩/卷绕/buf复用/缓存buf size/队列长度/低延时加速buf轮转/位图格式等，具体参考“各模块内存相关可优化配置”章节。
    4. 优化OS内存布局：SDK版本默认的DDR内存布局，特别是OS区域的布局可能不是实际产品最优的，往往需要结合产品功能进行二次调整，请参考《内存布局调整指南》。
    5. 优化size大的buffer：建议使用backtrace函数打印出分配内存的函数调用栈，找出内存较大的buffer展开业务分析是否可以优化，例如是否可透传指针不需要malloc内存和copy、是否可以复用其它buffer、buffer的大小是否可以减小等。backtrace函数Linux和C库都支持，可网上搜索用法。
    6. 优化产品镜像size：参考“Flash内存调优”章节。

    典型场景业务的MMZ内存占用数据，请参考《Hi35xxVxxx Memory Usage Statistics Report》。此外，客户业务的具体内存占用，需结合具体场景进行分析，下文介绍各模块MMZ内存占用及小型化可优化手段。

    VI

    须知：
    Hi3511CV100不支持bnr、3dnr、卷绕等所有pipe功能，不支持fmu。

    VI采集状态下最多会占用三个视频帧VB。一个用于当前帧采集，一个用于准备给下一帧采集，一个在轮转流程中（主要是后级模块占用）。对于Hi3511CV100，如果存在可变附属信息，会占用一到两个可变附属信息VB。

    • vi(%d)_model_%d：每路pipe需占用两个一定大小模板MMZ内存，大小与通路宽度相关，宽度小于等于4096时大小为16KB。
    • vi(%d)_lmf：每路pipe开启LMF功能时占用MMZ内存，用于存放LMF的系数，固定值4K。
    • vi(%d)_bnr_mot：每路pipe开启Bayer NR功能时需要占用的motion buffer内存，大小由处理图像大小的宽高决定，个数由ss_mpi_vi_set_pipe_bnr_buf_num接口配置，默认为2块，仅Hi3519DV500/Hi3516DV500支持。
    • vi(%d)_bnr_rnt：每路pipe开启Bayer NR功能时需要占用的rnt内存，大小由处理图像大小的宽高决定；离线时个数由ss_mpi_vi_set_pipe_bnr_buf_num接口设置，默认为2块。
    • vi(0)_bnr_tunl：每路pipe开启Bayer NR功能时需要占用的rnt内存，大小固定为4KB。
    • vi(0)_bnr_ref%d：每路pipe开启Bayer NR功能时需要占用的时域参考内存，大小由处理图像大小的宽高决定。
    • vi(0)_3dnr_para%d：每路pipe开启3DNR 功能时需要占用的模板内存，大小固定为4KB。
    • vi(0)_3dnr_ref%d：每路pipe开启3DNR 时域降噪功能时需要占用的参考内存，大小由处理图像大小的宽高决定。
    • vi(0)_3dnr_mad%d：每路pipe开启3DNR 时域降噪功能时需要占用的参考内存，大小由处理图像大小的宽高决定。
    • fmu0_wrap_buf：VI开启FMU WRAP模式时需要卷绕空间占用的内存，大小由ss_mpi_sys_set_fmu_attr接口page_num决定；使用卷绕空间可节省原本写出需占用的VB内存，仅Hi3519DV500/Hi3516DV500支持。
    • fmu0_cmp_head：VI开启FMU WRAP模式时需要占用的压缩头内存，大小由ss_mpi_vi_set_mod_param中最大宽高参数决定；使用卷绕空间可节省原本写出需占用的VB内存，仅Hi3519DV500/Hi3516DV500支持。
    • vi(0) wrap pool：每路pipe开启VI卷绕后的卷绕buffer，仅Hi3516CV610支持。
    • vi(0)_3dnr_stt%d：每路pipe开启3DNR 功能时需要占用的stt内存，大小由处理图像大小的宽高决定，仅Hi3516CV610支持。
    • vi(0)_subsidiary_0：开启随帧信息功能时需要占用的随帧信息内存，大小为ss_mpi_vi_set_chn_subsidiary_attr接口配置的随帧信息的宽乘高。仅Hi3511CV100支持。

    须知：

    VDEC MMZ占用分为buffer占用、轮转占用和设备占用。

    Buffer占用

    • vdec(%d)_stream：解码码流Buffer和用户数据Buffer相关内存，为用户指定大小和驱动内部分配之和。
    • vdec(%d)_pts_buf：用于存储码流Buffer管理的相关信息。

    设备占用

    • vfmw_scd_msg：SCD逻辑工作时需要的内存，固定值为40Kbytes。
    • vfmw(%d)_seg_buf：SCD切码流后存放内存，与分辨率相关，与协议无关。

    Hi3516DV500/Hi3519DV500：

    • vfmw(%d)_vedu_msg：VEDU逻辑工作时需要的内存，与模块参数中设置最大slice个数相关，默认模块参数（slice 600个）时大小为168KBytes。
    • vfmw_vedu_ext：VEDU逻辑工作时需要的内存大小100KBytes。

    Hi3511CV100：

    • vfmw_vdh_msg：VDH逻辑工作时消息池需要的内存，每个大小628KBytes，分配数量和用户在视频解码时模块参数中设置的vdh_msg_num相同，参考《MPP 媒体处理软件 V6.0 开发参考》ot_vdec_video_mod_param章节。
    • vfmw_vdh_ext：VDH逻辑工作时需要的片外内存大小1848KBytes。
    • vfmw_vdh_bin：VDH逻辑工作时用于存储bin流2368KBytes。
    • vfmw(%d)_ais_buf：用于缓存SVAC3.0协议中的语义分割图码流，具体大小由用户设置，用户不使能智能语义分割时不会分配，参考《MPP 媒体处理软件 V6.0 开发参考》ot_vdec_aiseg_param章节。
    • vfmw(%d)_priv_buf：用于缓存SVAC3.0协议中的隐私保护码流，驱动程序内部根据码流分辨率分配，非SVAC3.0协议解码时不会分配。
    • vfmw(%d)_crr_buf：用于缓存SVAC3.0协议中的CRR分片码流，驱动程序内部根据码流分辨率分配，码流中不存在CRR分片时不会分配。

    轮转占用

    • vdec(%d)_pic_vb：vb大小和个数都由用户配置。私有vb模式下，大小根据用户配置通道属性中frame_buf_size确定，个数根据用户配置通道属性中frame_buf_cnt确定。
    • vdec(%d)_tmv_vb：vb大小和个数都由用户配置。私有vb模式下，大小根据用户配置通道属性中tmv_buf_size确定，个数为 “参考帧+1”，其中参考帧个数根据用户配置通道属性中ref_frame_num确定。

    VPSS

    • vb_pool：Group占用两块VB (前级模块送来：当前工作VB+Backup 帧)，每个使能通道会获取通道大小的VB（通道模式为Auto时，为后端模块获取），硬件处理完成后会发送到后端绑定模块。如果需要做旋转/二级缩放功能，还需申请中间的临时VB（公共VB）。
    • vpss(%d)_model：每组需占用一定大小模板MMZ内存。大小与vpss_grp_cfg中的split_node_num和max_out_rgn_num有关。split_node_num和max_out_rgn_num越大，占用内存越大。
    • vmallocinfo：每组上下文需占用一定大小OS内存。总大小与组数量相关，组越多占用越大。

    Hi3519DV500/Hi3516DV500：

    • vpss(%d)_ref：3DNR参考帧，3DNR开启时分配，大小取决于max_width和max_height。
    • vpss(%d)_src：表示每组需占用MCF和DRC内存资源，约64K大小。
    • vpss(%d)_lmf：每组开启LMF功能时占用MMZ内存，用于存放LMF的系数，固定值4K。
    • vpss(%d)_angle_vel：vpss_grp_cfg中的is_dis_gyro_support开启时分配，每组占用约28K，大小固定。
    • fmu1_cmp_head：VPSS开启FMU1 WRAP模式时占用的压缩头内存，第一次配置卷绕通道压缩时分配，系统退出时释放。模块参数中的max_out_height越大，占用内存越大。
    • fmu1_wrap_buf：VPSS开启FMU1 WRAP模式时占用的内存卷绕空间，与页数有关。页数越大，占用内存越大。
    • vpss(%d)_wrap_pool_sup_xx：FMU1卷绕supplement内存VB池，固定8K。
    • vpss(%d)_direct_pool_sup_xx：FMU1直通supplement内存VB池，固定8K。
    • vpss(%d)_blend_pool：拼接融合VB池，与接口配置的buf_num和overlap_point相关。

    PCIV

    须知：
    Hi3519DV500/Hi3516CV610不支持PCIV。

    PCIV模块MMZ占用与PCIV模块的通道模式和类型有关。大致分为pcie-mcc消息池占用、window占用、DATA传输通道MMZ占用，FRAME传输通道VB轮转占用。

    • pcie-mcc消息池占用：

      用于pcie-mcc消息通信，在加载从片pcie驱动时指定位置与大小，大小固定为1M。

    • DATA传输通道MMZ占用：

      PCIV模块的每条DATA传输通道，包括发送端和接收端，都会配置用户指定长度的MMZ内存空间，用于存放用户调用接口发送进来的数据。MMZ大小由用户指定，建议为发送数据总长度的平均值的8倍且满足4字节对齐要求。

    • VB轮转占用：

      发送端通道接收前端模块送过来的VB，如果传输速率足够（图像小，帧率低），通道可只占用1个VB。如果传输速率不足（图像大，帧率快），通道最多可以占用8个VB。

      接收端从VB pool中获取VB，用来存放发送端发送过来的图像以及可能的附属帧信息和可变帧信息。如果传输速率足够（图像小，帧率低），通道可只占用1个图像VB以及可能的附属信息和可变帧信息VB。如果传输速率不足，通道最多可以占用8个图像VB以及可能的8个附属信息和可变帧信息VB。用户队列最大深度为8，最多可以占用8块用户VB，用户可以根据业务需求调增用户队列深度。

    优化镜像size

    优化镜像size的方法参见第5章节“flash内存调优”。

    限制栈大小

    默认的栈大小为8192KB，如果内存较小时，会导致线程创建不成功。根据实际的业务需要的栈空间，修改栈的限制大小为1024KB，如果业务更少则可以改成512KB或者更小。

    有两种方法可以修改栈大小：

    • 使用 ulimit –s 1024 命令，在应用程序启动之前调用一次；
    • 在main函数最开始调用函数 pthread_attr_setstacksize 也可实现对单个应用程序修改栈空间的目的。

    优化代码中内存使用

    优化代码中内存使用，特别是对栈、堆、常量、全局变量的使用，主要需要注意：

    • 避免应用程序代码中申请后不用的变量；
    • 不要随意申请大块的内存，够用即可；
    • 冗余的内存使用还包含不用的功能模块的初始化。

    应用程序中禁用fork、system等进程创建函数

    由于主进程的数据段占用内存已经很多，如果fork子进程必定消耗大量内存而且会有大概率失败，那么应用程序中应该禁用fork、system等进程创建函数：如bspmm调用、mkfs.vfat调用等。

    CMA相关

    在Hi3519DV500项目中，系统默认打开了CMA，Hi3516CV610/Hi3511CV100默认关闭了CMA。打开CMA后，系统会默认保留部分内存。这部分保留的内存可能只会使用其中一部分。因此，为了节省内存，客户可以采取以下两种方法：

    1. 调整系统保留的内存。

      客户可以通过cat /proc/meminfo命令查看当前系统保留的CMA内存和这部分内存的使用情况，其中CmaTotal是当前系统保留的CMA内存，CmaFree是剩余的内存：

      CmaTotal: 16384 kB

      CmaFree: 16068 kB

      客户可以通过修改内核配置调整保留内存的大小：

      Device Drivers->Generic Driver Options ->Size in Mega Bytes

      修改内核配置后，请重新编译内核。

    2. 关闭CMA。

      如果客户不使用CMA功能，可以通过修改内核配置关闭CMA：

      Kernel Features->Contiguous Memory Allocator

      修改内核配置后，请重新编译内核和ot_osal.ko以及ot_mmz.ko。

    通过代码裁剪编译优化镜像size

    为了提升开发效率和降低维护成本，一般是多产品共平台代码，但每个产品都有功能差异，功能代码尽量精细化使用宏隔离，每个产品有独立的功能宏集合配置脚本，即不破坏平台兼容多产品，同时又有利于每款产品的size小型化。

    自动优化掉不使用的函数

    编译选项说明：

    -ffunction-sections 编译源文件时，为每个function分配独立的section。

    -fdata-sections 编译源文件时，为每个data分配独立的section。

    --gc-sections 链接时，以section为最小处理单元，只有当section中有symbol被使用，才将该section链接到output中。

    我们在编译选项里面加上 -ffunction-sections -fdata-sections, 然后在链接选项里面加上 -Wl,-gc-sections（注意：一旦使用-Wl,-gc-sections将无法使用gdb调试，也无法使用gprof）

    • SDK MPP生成库时，Makefile.param已加入-ffunction-sections -fdata-sections编译选项；客户在链接生成应用程序时加入 -Wl，-gc-sections，能有效减小应用程序大小，剔除掉没有使用到的函数。
    • 客户自己开发的应用程序静态库，也需按如上方法配置。

    说明：
    此方法仅对静态库链接有效。

    标准C库/C++库链接裁剪

    标准C库/C++库是个大集合，产品程序可能仅使用了标准库中不到一半的函数，此时可考虑标准库的链接裁剪，自动优化掉不使用的函数。

    如果产品的可执行程序不多，建议使用标准库的静态库，可执行程序再配合链接选项”-Wl，-gc-sections”优化掉不使用的函数，动态库则不需要安装到产品设备里。
